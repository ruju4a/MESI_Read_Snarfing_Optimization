Read-Snarfing Optimization for MESI L1
Report by: rspalimk

1. Optimization Selected
I implemented a read-snarfing optimization for the MESI L1 coherence controller. Read snarfing allows an L1 cache that does not currently hold a valid copy of a cache line to opportunistically install that line when it snoops a broadcast GetSResp generated by another core’s read miss. The goal is to reduce repeated shared-read misses and lower coherence traffic for data that becomes shared across multiple private L1 caches.

2. Implementation Changes
The optimization was implemented conservatively so that the original MESI behavior remains unchanged when the optimization is disabled.
The main changes were:
Added a coherence_opt parameter to the MESI L1 controller so the optimization can be enabled or disabled at runtime.
Modified handleGetSResp() in MESI_L1.cc to distinguish between:
a normal demand response that matches a local outstanding miss, and
an unsolicited snooped GetSResp seen on the bus.
When coherence_opt is disabled, unsolicited GetSResp messages are discarded, preserving the baseline design.
When coherence_opt is enabled, an unsolicited GetSResp may be used as a snoop fill if the local line is absent or currently Invalid. In that case, the cache installs the payload and transitions the line to S state.
Updated the bus behavior so that in optimized mode only GetSResp is broadcast to peer high-side ports. Other coherence events continue to use normal point-to-point routing, which avoids breaking the rest of the hierarchy.
Updated the Prospero test harness so that coherence_opt is passed into each L1 and bus broadcast is enabled only in optimized mode.

3. Directed Testcase
The directed testcase uses four cores and a single shared cache line at address 0x1000.
The trace pattern is:
Core 0: one write to the line
Core 1: one read to the same line
Core 2: two later reads to the same line
Core 3: two later reads to the same line
This pattern isolates the read-snarfing effect. Core 0 first writes the line, establishing ownership of the cache line in the hierarchy. Core 1 then performs the first read miss, which generates the GetSResp carrying the data. Cores 2 and 3 are delayed long enough that, in optimized mode, they can snoop that broadcast GetSResp, install the line in S state, and avoid sending their own first GetS requests. Their second reads confirm that the line remains cached locally.

4. Results
For the current testcase, the expected and reported behavior is:
Baseline MESI (OPT_ON=0)
l1cache1 getS_sent = 1
l1cache2 getS_sent = 1
l1cache3 getS_sent = 1
Optimized MESI (OPT_ON=1)
l1cache1 getS_sent = 1
l1cache2 getS_sent = 0
l1cache3 getS_sent = 0
Interpretation:
l1cache1 is the first reader, so it must still issue the demand GetS.
l1cache2 and l1cache3 benefit from read snarfing. They install the line by snooping core 1’s broadcast GetSResp, so their later reads hit locally and do not generate GetS.

5. Quantitative Improvement
Considering the three reader cores (l1cache1, l1cache2, and l1cache3):
Baseline total GetS count = 1 + 1 + 1 = 3
Optimized total GetS count = 1 + 0 + 0 = 1
So the optimization reduces shared-read request traffic by:
Absolute reduction: 2 GetS transactions
Relative reduction: 2 / 3 = 66.7%
For the two later readers that directly benefit from snarfing:
Baseline: 2 GetS requests total
Optimized: 0 GetS requests total
So for those readers, the reduction is:
Absolute reduction: 2 GetS transactions
Relative reduction: 100%

6. Conclusion
The read-snarfing optimization successfully reduces coherence traffic for repeated shared reads in this directed MESI L1 testcase. The first reader still incurs the normal read miss, but later readers can obtain the line by snooping the broadcast GetSResp and installing it locally in S state. This preserves the baseline MESI behavior when the optimization is disabled while reducing shared-read request traffic when enabled.
